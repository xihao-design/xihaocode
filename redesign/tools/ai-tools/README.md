# AI 库（/ai/）数据与流程说明

> 这一层服务的是「AI 工具与在线服务」类目 —— 它与软件库、技能库最大的不同是
> **没有安装包、没有网盘交付物**。在线工具不能转存，所以这一类的价值不在「给你文件」，
> 而在把三件事钉死：官网、费用形态、**国内能不能用**。

## 一条内容的合规边界（先说清楚，这决定什么能收、什么不能收）

| 类别 | 具体内容 | 能不能收 |
| --- | --- | --- |
| **事实** | 工具名称、官网地址、开发方、是否开源、源码仓库、免费额度形态、支持平台 | ✅ 可收，逐条核实官网 |
| **人判断字段** | 「从中国大陆是否要自备网络条件」「中文支持程度」 | ✅ 可收，但必须人工核实后标注 |
| **中文文案** | 一句介绍、功能要点、适用人群、使用步骤 | ✅ 可收，但**必须自己写** |
| **他人的编辑内容** | 别的工具目录站写的介绍、评测、榜单、分类结构 | ❌ **绝不搬运** |

**为什么文案必须自己写**：整站抓取别的目录站的内容，一是版权问题，
二是百度/Google 会把采集站判为重复内容并降权 —— 那正好是「想提高搜索流量」的反面。
事实可以共享（名称、官网就是事实），表达不能共享。

**站内已有的同类原则**（保持一致，不要另立一套）：
- 软件库：`curation.json` 里拒绝空文案，`descOverride` 用于覆盖与事实不符的原文
- 技能库：协议看内容不看文件名、聚合仓库只当发现索引不当打包来源
- AI 库：**事实可脚本批量导入，文案由人过目**

## 数据流

```
调研/核实（会话内 AI + web_fetch 逐个打开官网）
        ↓  产出「事实包」：一个分类组一个 JSON
redesign/tools/ai-tools/sources/imported/<batch>.json
        ↓  npm run ai:import
redesign/content/tool/<分类>/<slug>.json      ← 站内条目（per-item JSON）
        ↓  npm run build
redesign/dist/ai/index.html + category/<id>.html + <slug>.html
```

### 事实包的字段

一条记录长这样（字段名与 `import.mjs` 的读取一致）：

```json
{
  "name": "Dify", "nameZh": "Dify", "slug": "dify",
  "vendor": "苏州语灵人工智能科技有限公司",
  "site": "https://dify.ai", "cat": "prompts",
  "opensource": true, "repo": "https://github.com/langgenius/dify",
  "freeTier": "freemium",
  "needsVpn": false, "zhSupport": true,
  "platforms": ["网页", "Docker"],
  "oneLine": "开源大模型应用开发平台，用可视化编排搭建提示词与工作流",
  "pricingUrl": "https://dify.ai/zh/pricing/dify-cloud",
  "facts": ["提供可视化提示词编排与工作流画布", "内置 RAG 知识库与多种模型接入"]
}
```

- `freeTier` 只认四个值：`free` / `freemium` / `paid` / `trial`，其它值导入器直接拒收
- `opensource: true` **必须**带 `repo` —— 声称开源却没有仓库地址等于无法核实
- `site` 必须是 https 且能打开；`pricingUrl` 没有就留 `null`，**不要猜路径**
- `needsVpn` 是访问体验判断，脚本在服务器侧测得通畅不代表用户侧通畅，必须人工核

## 导入器（`npm run ai:import`）

三条设计决定，每条都对应一个实际踩过的坑：

1. **幂等，且不覆盖人工内容**。已有条目的文案字段默认保留 ——
   运营中会手工润色文案、补 `accessNote`，重跑导入不能把这些改回去。
   `--force` 只覆盖**事实**字段；要按新规则重算文案得显式加 `--regen-copy`
   （「补字段」和「重写文案」是两件事，混在一起就会在补字段时把人的润色冲掉）。
2. **跨事实包查重**。事实包是分批交来的，同一个工具被两批收进来时 slug 往往不同
   （实测：`kling` vs `kling-ai`、`designkit` vs `meitu-designkit`、
   `zhiwen` vs `xunfei-zhiwen`、`jimeng` 两批各一份）。
   批内查重看不见这种重复，所以**按官网地址再查一遍已落盘的条目**，
   同一官网不同 slug 一律拦下并报出双方，站内不会出现两个详情页。
   （同 slug 的重复是「重新导入自己」，属正常的幂等更新，不算冲突。）
3. **文案由事实拼装，不编新事实**。`desc` 里的每一句都能追到事实包的某个字段；
   拿不到就退回不含事实断言的通用句。实测踩到的两个坑：
   - 「快手推出的 AI 视频生成平台」+ 前半句「由快手推出」→ 重复。
     拼装侧负责削掉事实包里重复的厂商前缀（调研方写一句话时不知道这里的拼接规则）。
   - 「OpenAI 开源」削前缀时留下一个孤立的「的」→「是 OpenAI 的产品，的语音识别模型」。
     修法是让 `开源的` 分支排在裸 `开源` 前面，并且裸形式连带吃掉后面的「的」。

## 两级分类：父类 → 功能子类

目录页是「按分类分区堆叠」，每个分类区块里还有一行**按功能**的标签。
分类来自 `site.config.json` 的 `toolCategories`（16 个），功能子类来自
`redesign/content/tool-subcats.json`。

```
/ai/                              目录页：16 个分类区块，每块带「按功能」标签行
/ai/category/audio               分类页：该分类全部条目 + 「按功能细分」卡片
/ai/category/audio/transcription 子类页：只含该功能子类的条目
/ai/whisper                      工具详情页（URL 与分类无关，永远只有一份）
```

### 成员归属是人工判定的，不要改成关键词匹配

**这一条是有实测代价的**。先用关键词跑过一遍 149 条：

| 关键词匹配的结果 | 问题 |
| --- | --- |
| `ACE Studio`（歌声合成）→ 判进「音轨分离」 | 只因介绍里有「分离」二字 |
| `魔音工坊` / `讯飞智作`（配音平台）→ 判进「语音克隆」 | 只因介绍里有「音色克隆」四个字 |
| audio 的「语音合成/配音」与「语音克隆」→ 命中**完全相同的 5 条** | 非互斥匹配，产出两个几乎一样的页面 |
| chatbot 三个子类 → 全部命中同样 10 条 | 同上 |
| 47 个候选子类里只有 17 个能到 4 条 | 摊薄后大量子类不够门槛 |

子类页归错类比没有子类页更糟 —— 访客一眼就看出不对。所以 `tool-subcats.json` 里的
`slugs` 数组就是判定结果，构建期只做校验与统计，不做推导。

### 两道产出闸门（`build.mjs` 执行，逐条打印原因）

| 闸门 | 理由 |
| --- | --- |
| 成员数 ≥ `minItems`（默认 4） | 一两条的子类页是薄内容，对访客和搜索引擎都是负分 |
| 成员集合 ≠ 父类全集 | `chatbot` 的「通用对话助手」就是全部 10 条，产出会是父类页的副本 |

**不够门槛的子类仍然显示**（作为分类页上的筛选标签，带 slug 数），只是：
不产出页面、不进 sitemap、不进侧栏。门槛管的是「要不要单独做一页」，
不是「这个概念值不值得筛」——这两件事混为一谈会把筛选器一起砍掉。

构建报告会打印「子类未产出页面 N 个（原因）」，**补几条工具就能跨过门槛自动亮，不用改代码**。

### 校验（构建期，写错会报出来）

- 子类的 `cat` 必须在 `toolCategories` 里
- 子类的 `slug` 必须是显式给出的 ASCII（中文名推不出拼音）
- 每个成员 slug **必须属于该父类** —— 实测据此修掉过 3 处人工错记
  （`meitu-designkit` 实际在 design 不在 image、`jimeng` 在 image 不在 video、
  `xunfei-zhiwen` 在 design 不在 work）
- 子类名在同一父类下不得重复；解析后成员为空的子类跳过

### 加一个子类

1. 在 `content/tool-subcats.json` 对应父类的 `items` 里加一项：`slug`（ASCII）、
   `name`、`desc`、`slugs`（成员）
2. `npm run build` —— 看报告里它是否产出了页面；不够门槛会说明原因与当前条数
3. 跨子类重复成员是允许的（子类是功能视角，一个工具能做两件事就出现在两处），
   但**成员集合与父类相同**会被拦下

### 相对链接的深度（很容易写错）

| 页面 | depth | 链到工具详情页 |
| --- | --- | --- |
| `/` 首页 | 0 | `ai/<slug>.html` |
| `/ai/` 与 `/ai/<slug>` | 1 | `<slug>.html` |
| `/ai/category/<cat>` | 2 | `../<slug>.html` |
| `/ai/category/<cat>/<sub>` | 3 | `../../<slug>.html` |

分类页链到子类页要多带一级：`<cat>/<sub>.html`（写成 `<sub>.html` 会让该分类下所有子类链接死链 ——
实测 22 个分类页全挂，被 `check-dist` 报出来）。

## 页面产出的门槛

| 产物 | 门槛 | 不够时 |
| --- | --- | --- |
| `/ai/` 目录页 + 侧栏/导航项 + sitemap 条目 | `minItems: 24`（`site.config.json` 的 channels.ai） | 一律不产出，首页频道卡退回「筹备中」并显示「已有 N/24」 |
| `/ai/category/<id>` 分类页 | `toolCategoryMinItems: 4` | 不产出页面，筛选条上也不出现该分类 |
| `/ai/<slug>` 详情页 | 条目 `status: "ok"` 且 `tagline`/`desc` 齐全 | 跳过并打印警告 |

分类页是独立 URL 而不是只做筛选器，理由：一个可索引的
`/ai/category/writing` 能吃到「AI 写作工具」这类类目词，前端筛选器做不到这件事。

## 加一个分类 / 加一批工具

1. 在 `site.config.json` 的 `toolCategories` 里加分类（`id` 必须与条目的 `cat` 一致）
2. 把事实包放进 `redesign/tools/ai-tools/sources/`，`npm run ai:check` 先干跑
3. 看清「问题」列表：分类未识别、官网重复、平台值未识别都会在这里报出来
4. `npm run ai:import` → `npm run build` → `npm run check`

## 已知的人工环节（脚本替不了）

- **`needsVpn` 与 `zhSupport` 必须人工核实**。这是本站与「随便抄一份清单」的差别所在，
  也是这一类目最有价值的一栏。
- **文案润色**。导入器拼出来的是「事实的规范化表达」，读着通顺但没有观点、
  没有「这个工具适合什么人」的判断。要真正吃到长尾词，`desc` / `features` 应该逐个过一遍手。
- **官网失效巡检**。在线工具下线比开源项目停维护更快，
  `tools/ai-tools/` 目前**没有**链接巡检（软件库那套 `verify-live.mjs` 只覆盖网盘链接）。
  条目多起来之后需要补一个：批量 HEAD 请求官网，非 200 的报出来人工确认。
